# Skill 评审流程

这份文档说明一个 Skill 从“有人推荐”到“正式收录”的流程。

我们的目标不是把所有项目都收进来，而是帮普通人少走弯路。一个 Skill 就算 stars 很高，也不一定适合放进正式推荐；一个项目 stars 没那么夸张，但场景清楚、文档完整、普通人能用起来，也可能值得收。

## 状态怎么分

| 状态 | 含义 | 放在哪里 |
| --- | --- | --- |
| 候选 | 有人推荐，或我们觉得可能有价值，但还没核查完。 | `sources/`、issue、collection 的候选区 |
| 观察中 | 方向有价值，但维护、许可证、可用性或风险还没看清楚。 | Skill 卡片或 collection 里标明 |
| 可参考 | 有价值，但不适合普通人直接用，或者需要明显改造。 | `catalog/` 卡片 |
| 推荐 | 来源清楚、许可证清楚、能解决具体任务，且有比较明确的上手路线。 | `catalog/`、`collections/`、`catalog/INDEX.md` |
| 不推荐 | 风险明显、长期失效、用途不合适，或无法复现。 | 一般不进正式推荐，必要时在评审记录里说明 |

对应到 YAML frontmatter：

```yaml
status: recommended
```

可选值：

- `recommended`
- `reference`
- `watching`
- `not_recommended`

## 推荐位怎么分

每个小类尽量只留 2 到 3 个正式位置：

| 推荐位 | 适合谁 | YAML 值 |
| --- | --- | --- |
| 最省心 | 普通人第一次用，优先选它。 | `easiest` |
| 进阶 | 已经会用 Agent，愿意处理一些环境和配置。 | `advanced` |
| 可改造 | 想二次开发、接入流程、改成自己版本的人。 | `remixable` |

“最省心”可以是独立 Skill，也可以是我们给复杂 Skill 做好的 starter 路线。

## 从推荐到收录

### 第 1 步：收到候选

候选来源可以是：

- GitHub issue。
- 朋友或读者推荐。
- 我们自己搜索到的项目。
- 官方示例、课程、社区合集。
- 已有 Skill 的依赖或同类项目。

先不要急着写正式卡片。先记下：

- 名称。
- 原始链接。
- 所属大类和小类。
- 它解决什么具体任务。
- 推荐它的人为什么觉得有用。

### 第 2 步：做基础核查

最少要看这些：

- 原始链接能不能打开。
- 作者、组织或维护者是否清楚。
- 许可证是否清楚。
- README、示例或文档是否说明怎么用。
- 最近是否还在维护。
- 是否有真实输入和输出示例。
- 是否涉及隐私、版权、账号安全或违规用途。

如果许可证找不到，先放候选，不写正式推荐。

### 第 3 步：放进小类

不要只按项目名字分类。先问：

- 用户拿它完成什么任务？
- 输入材料是什么？
- 输出结果是什么？
- 它和同小类其他 Skill 比，强在哪里？
- 它适合“最省心 / 进阶 / 可改造”里的哪一位？

如果放不进任何明确小类，先不要收。

### 第 4 步：试用或读到能判断

理想情况是实际跑一次。

如果暂时不能跑，也至少要读到能判断：

- 安装步骤是否清楚。
- 依赖是否过重。
- 普通用户容易卡在哪里。
- 输出是不是具体文件、结构化结果或可复用流程。
- 它是不是只是一段泛泛 prompt。

试用记录可以放到 `reviews/`。不需要写长文，但要写具体。

### 第 5 步：决定状态

可以按这个表判断：

| 情况 | 建议状态 |
| --- | --- |
| 来源、许可证、文档、用途都清楚，能解决具体任务。 | 推荐 |
| 有价值，但普通人很难直接用。 | 可参考 |
| 方向不错，但许可证、维护或可用性还不确定。 | 观察中 |
| 链接失效、无法复现、风险明显或用途不合适。 | 不推荐 |

如果某个小类已经有 2 到 3 个推荐位，新项目不是自动加进去，而是和已有条目比较。更好的项目可以替换旧项目；旧项目可以降为可参考或观察中。

### 第 6 步：写卡片和合集

正式进入 `catalog/` 时，至少要补：

- YAML frontmatter。
- 基本信息。
- 一句话说明。
- 适合谁、不适合谁。
- 典型场景。
- 怎么使用。
- 优点、限制、风险。
- 结论。

同时更新：

- `catalog/INDEX.md`
- 对应的 `collections/*.md`
- 必要时补 `reviews/`
- 如果普通人上手很容易卡，再考虑补 `kits/`

## 什么情况要降级

已经推荐的 Skill 也会变化。遇到这些情况，要重新评审：

- 原仓库删除、归档或长期不维护。
- 许可证变化，或许可证信息被移除。
- 安装方式失效，主要依赖不可用。
- 新版本引入明显风险。
- 文档和实际行为严重不一致。
- 出现更适合普通人的同类 Skill。

降级不是否定原作者，只是说明它现在不适合放在这个推荐位。

## 复核节奏

高优先级 Skill 每月简单复核一次：

- 链接是否有效。
- stars、forks、release 或最近更新时间是否有明显变化。
- README 是否变化。
- 许可证是否变化。
- starter 是否还能跑。
- 是否有新的安全或隐私风险。

低优先级 Skill 可以按需复核。有人报告问题时优先处理。

## 评审时不要做什么

- 不要因为 stars 高就直接推荐。
- 不要因为名字像 Skill 就收。
- 不要默认复制第三方完整内容。
- 不要收许可证不清的项目作为正式推荐。
- 不要把普通 prompt 包装成高质量 Skill。
- 不要为了凑满 3 个推荐位降低标准。

## 最小评审记录

如果时间很少，至少留下这几项：

```text
Skill 名称：
原始链接：
所属小类：
候选推荐位：
许可证：
核查日期：
试用情况：
主要优点：
主要风险：
当前结论：候选 / 观察中 / 可参考 / 推荐 / 不推荐
```

这几项足够让后来的人接着判断，不用从零开始。

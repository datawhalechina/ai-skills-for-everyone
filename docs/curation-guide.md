# 收录标准

这个项目的价值不在于链接多，而在于筛过，而且是按场景筛。每个条目进入 catalog 之前，至少要过一遍下面这些标准。

完整流程看：[Skill 评审流程](review-process.md)。

## 推荐位规则

每个小类尽量只保留 2 到 3 个正式推荐：

| 推荐位 | 判断标准 |
| --- | --- |
| 最省心 | 普通人最容易开始用：任务单一、输入输出直观、README 清楚、试跑能成功。中文教程、starter、清楚的输入输出目录和排错说明都是加分项，不是硬门槛。 |
| 进阶 | 能力更完整，适合已经会用 Agent 的人，允许有一定环境配置。 |
| 可改造 | 适合开发者或轻技术用户继续改，或者适合作为别的 Skill / 工作流的底座。 |

“最省心”可以是独立 Skill，也可以是我们给复杂 Skill 做的 starter 路线。判断标准不是有没有 starter，而是普通人能不能理解它解决什么、第一次能不能在 Agent 帮助下跑出结果、出了问题能不能定位到具体环节。

候选很多时，不要全塞进正式推荐。先放到候选来源，等试用、许可证、维护状态和场景匹配度都看清楚，再决定替换哪个推荐位。

如果一个小类只有 1 个真正靠谱的项目，就只放 1 个。空位写“待搜罗”，不要为了凑满而降低标准。

## Skill 卡片元数据

正式进入 `catalog/` 的 Skill 卡片，顶部都要加 YAML frontmatter。规则是：

- 字段名用英文，比如 `category`、`status`、`checked_at`。
- 给程序用的值尽量用英文枚举，比如 `recommended`、`advanced`、`intermediate`。
- 给读者看的展示名可以写中文，比如 `category_name: 写作与办公`。
- 路径用相对路径，方便 GitHub 直接跳转。

推荐位字段统一用：

| 值 | 含义 |
| --- | --- |
| `easiest` | 最省心 |
| `advanced` | 进阶 |
| `remixable` | 可改造 |

收录状态字段统一用：

| 值 | 含义 |
| --- | --- |
| `recommended` | 推荐 |
| `reference` | 可参考 |
| `watching` | 观察中 |
| `not_recommended` | 不推荐 |

难度字段统一用：

| 值 | 含义 |
| --- | --- |
| `beginner` | 新手 |
| `intermediate` | 中等 |
| `advanced` | 进阶 |
| `developer` | 开发者 |

## 先定场景

不要一开始就搜“best AI skills”。先写清楚用户任务：

- 用户是谁。
- 他要完成什么。
- 输入材料是什么。
- 期待输出是什么。
- 这个任务有没有隐私、版权或事实核查风险。

场景定清楚以后，再去找 Skill。找回来的项目先放进对应 collection，再决定要不要写成 catalog 卡片。

## 基本条件

- 来源公开可访问。
- 许可证清楚。
- 作者、组织或维护者能查到。
- README、示例或文档能说明它怎么用。
- 它解决的是具体任务，而不是只有一句泛泛提示词。
- 能放进至少一个明确场景，不能只因为名字好听就收录。
- 使用前依赖要能列清楚，尤其是外部 API key、账号权限、本地运行环境和会联网的服务。

## 使用前依赖清单

每个正式推荐 Skill 都应该尽量写清楚“开始前要准备什么”。这一步要在用户运行命令、上传文件或填写密钥之前完成。

依赖清单至少检查这些：

| 依赖类型 | 例子 | 为什么要提前说 |
| --- | --- | --- |
| 模型 / API key | Claude、OpenAI、Anthropic、Gemini、自定义中转 API | 没有 key 或模型能力不够，Skill 可能看起来“能跑”，但输出质量很差。 |
| 第三方账号权限 | GitHub、Notion、Google Drive、飞书、Slack、Zotero | Agent 可能需要登录、读写文件或访问私有数据。 |
| 本地运行环境 | Python、Node.js、npm、pnpm、Docker、Java | 没装环境会卡在第一条命令，普通用户会误以为 Skill 坏了。 |
| 本地工具 | Chrome、PowerPoint、LibreOffice、pandoc、pdftotext、ffmpeg | 很多 Skill 实际依赖外部程序完成渲染、转换或解析。 |
| 网络与证书 | GitHub、arXiv、npm、pip、公司代理、SSL 证书 | 下载失败、证书失败和代理问题是最常见的“玄学坏掉”。 |
| 本地数据路径 | PDF、图片、Obsidian vault、Zotero storage、输入/输出目录 | 路径不清楚会导致文件写错位置，甚至污染真实资料库。 |

如果依赖项里包含 API key 或登录账号，卡片里要提醒：不要把密钥写进提示词、截图、公开仓库或 issue；让 Agent 先列依赖和风险，再决定是否继续。

## 高星怎么理解

“高星”不是一个死数字。不同领域的基准不一样。

优先看这些信号：

- GitHub stars。
- fork 数。
- 最近更新时间。
- issue 和 PR 活跃度。
- 是否被官方文档、课程或社区反复引用。
- 是否有真实使用示例。

初期可以先把 100 stars 作为 GitHub 项目的参考线，但不要机械执行。官方示例、细分领域项目、新项目里的好东西，也可以进入候选，但要说明为什么值得收。

## 许可证

优先收录许可证明确的项目，比如 MIT、Apache-2.0、BSD、MPL、CC-BY 等。

如果许可证不清楚：

- 可以放进候选来源。
- 不放进正式推荐。
- 不复制内容。
- 在卡片里标为“许可证待核查”。

## 推荐等级

每个 Skill 卡片可以给一个简单判断：

- 推荐：来源清楚、文档完整、可复用性强。
- 可参考：有价值，但需要改造或文档不够完整。
- 观察中：方向有意思，但维护、许可证或可用性还不确定。
- 不推荐：风险明显、无法复现、长期失效或用途不合适。

## 安全和伦理边界

不收录这些内容：

- 绕过平台规则、考试规则或付费限制。
- 伪造身份、冒充真人或欺骗审核。
- 批量抓取隐私信息、账号信息或敏感数据。
- 明显侵犯版权或诱导用户上传不该上传的材料。

如果一个项目本身有价值，但部分用法有风险，卡片里要写清楚边界。

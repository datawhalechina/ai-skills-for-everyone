# 第三方 Skill 处理原则

这个项目主要收录别人已经开源的 Skill。我们要做的是筛选、解释、试用和整理上手路线，不是把别人的项目搬成自己的项目。

## 基本原则

- 优先链接原始项目，不默认复制完整内容。
- 只收录来源清楚、许可证清楚、用途边界清楚的项目。
- 中文说明、starter、排错文档可以由我们自己写。
- 如果必须提供备用下载，要写清楚来源、版本、日期、许可证和为什么需要它。
- 如果许可证不清楚，只能放进候选来源，不放进正式推荐。

## 本仓库自己的许可边界

本仓库采用双许可证：

- 原创文档、教程、Skill 卡片、评测、整理内容：CC BY-NC-SA 4.0。
- 本仓库自己编写的脚本、配置、检查工具和代码片段：MIT。

这两个许可证只覆盖本仓库的原创内容，不覆盖第三方 Skill、第三方项目、原始代码、模型、模板、图片、字体、数据和文档。

除非明确说明，本仓库不对第三方项目内容重新授权。

## 什么可以放进本仓库

这些内容通常可以放：

- 我们自己写的中文介绍、教程、排错说明和试用记录。
- 指向原项目的链接、版本号、核查日期和许可证信息。
- 我们自己制作的 starter 工作区。
- 为了上手体验写的小脚本、提示词和样例材料。
- 少量必要引用，但不能替代原项目文档。

这些内容不要默认放：

- 第三方 Skill 的完整源码或完整 `SKILL.md`。
- 第三方项目的完整压缩包。
- 来路不明的二次搬运文件。
- 许可证不允许再分发的模型、模板、图片、字体、数据集或文档。
- 包含账号、密钥、客户资料、公司内部资料的文件。

## 什么时候可以镜像或备用下载

一般情况下，不做镜像，只链接原始项目。

只有同时满足这些条件，才可以考虑备用下载：

- 原项目许可证允许再分发。
- 备用文件来自原始项目，不是来路不明的搬运版本。
- 记录了原始链接、版本号或 commit、下载日期、许可证。
- 文件没有被我们偷偷改过；如果改过，要明确写成“改造版”。
- 备用下载只是为了 GitHub 打不开或下载不稳定时使用，不替代原作者主页。

备用下载说明至少要包含：

```text
原始项目：
原始链接：
许可证：
版本 / commit：
下载或打包日期：
备用下载地址：
是否修改过：
用途说明：
```

## 百度网盘、网盘和压缩包

可以提供备用下载地址，但要克制。

适合放的：

- 我们自己写的 starter 工作区压缩包。
- 许可证允许再分发的原项目 release 包。
- 原项目公开发布、来源清楚、版本清楚的文件。

不适合放的：

- 许可证不清楚的第三方完整项目。
- 从别人网盘、群文件、论坛下载来的二手包。
- 混入依赖、缓存、输出结果、个人配置或密钥的压缩包。
- 未经允许的商业模板、字体、图片、报告、数据集。

如果提供网盘下载，旁边要写：

- 这是备用下载，不是原始来源。
- 优先使用原项目链接。
- 文件对应的版本和日期。
- 许可证和版权仍归原作者。

## 改造版怎么处理

如果我们改了第三方 Skill，不要假装它还是原版。

文件或说明里要写清楚：

- 基于哪个原项目。
- 原项目许可证是什么。
- 我们改了什么。
- 改造版放在哪里。
- 用户应该优先看原版，还是优先看改造版。

如果改动只是中文教程、starter、示例材料，不算改第三方源码。说明里写“基于某项目整理的上手路线”就够了。

## 许可证怎么写

每个正式 Skill 卡片都要写许可证。

如果许可证是 MIT、Apache-2.0、BSD 这类宽松许可证，也不代表可以不署名。卡片里至少保留：

- 原项目名称。
- 作者或组织。
- 原始链接。
- 许可证名称。
- 核查日期。

如果许可证是 GPL、AGPL、CC-BY-SA 这类有更多条件的许可证，不要急着复制内容。先只写索引和说明，等确认边界后再决定是否提供 starter 或镜像。

如果没有许可证：

- 不写成正式推荐。
- 不复制内容。
- 可以放进候选来源。
- 标记为“许可证待核查”。

## 隐私和输入材料

很多 Skill 会处理文档、表格、会议记录、客户资料或公司材料。我们给普通人写教程时，要明确提醒：

- 不要上传公司机密、客户隐私、合同、账号、密钥和未公开数据。
- 不要把没有授权的报告、课程、书籍、图片或模板上传给外部模型。
- 输出里的事实、数据、引用和结论都要人工复核。

## 一句话版本

能链接原项目，就不要搬运。  
能写上手路线，就不要复制源码。  
真要备用下载，就把来源、版本、许可证和边界写清楚。

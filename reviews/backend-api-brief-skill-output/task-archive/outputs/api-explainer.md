# 给自己看的接口说明：任务归档

## 这件事后端要做什么

“任务归档”不是把任务删掉，而是让任务进入一个历史状态：平时列表不显示，但以后还能查到，必要时还能恢复。后端需要负责三件事：

- 记录任务已经归档。
- 判断谁能归档、谁能恢复、谁能查看归档任务。
- 让任务列表默认不显示归档任务，同时保留查询入口。

## 你需要先决定什么

- 哪些任务可以归档：只有已完成任务，还是进行中的任务也能归档？
- 恢复后任务回到哪里：回到归档前状态，还是固定回到“已完成”？
- 普通成员能不能看到别人归档的任务？
- 是否要记录归档原因？
- 归档任务还要不要进入报表统计？

这些不是技术细节，是业务规则。先决定这些，开发才不会猜错。

## 它大概会有哪些接口

你可以理解成后端会多几个“入口”：

- 归档任务：把某个任务移到历史区。
- 恢复任务：管理员把归档任务恢复出来。
- 查看归档任务：在任务列表里加一个筛选条件，例如“只看归档”。

开发文档里可以写成：

| 你要做的事 | 给开发看的接口方向 |
| --- | --- |
| 归档任务 | `POST /tasks/{task_id}/archive` |
| 恢复任务 | `POST /tasks/{task_id}/restore` |
| 查看归档任务 | `GET /tasks?archived=true` |

## 哪些地方容易出问题

- **权限问题**：不能只靠前端隐藏按钮，后端必须判断用户是不是任务负责人或项目管理员。
- **数据问题**：如果任务状态存在数据库 enum 里，新增 `archived` 可能需要 migration（数据库结构变更）。
- **历史数据问题**：如果以前已经有“归档”的旧数据，可能要 backfill（补齐历史数据）。
- **列表兼容问题**：默认任务列表排除归档任务后，报表、看板或外部调用可能少数据。
- **恢复规则问题**：如果不记录归档前状态，恢复后不知道该回到哪个状态。

## 你可以这样问开发

- 当前任务状态是普通字段，还是数据库 enum？
- 归档需要新增 `archived_at`、`archived_by` 吗？
- 恢复任务时能不能回到归档前状态？
- `GET /tasks` 默认排除归档任务，会不会影响现有页面或报表？
- 普通成员查看归档任务的权限怎么判断？

## 暂时不要做什么

- 不要把归档当成删除。
- 不要让前端单独控制权限。
- 不要在没确认数据库和发布顺序前直接改线上库。
- 不要一开始就做批量归档、自动归档或审批流，第一版先做最小闭环。

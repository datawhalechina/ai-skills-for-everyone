# 给自己看的接口说明：邀请成员加入团队

## 这件事后端要做什么

“邀请成员加入团队”不是简单发一封邮件。后端至少要处理四件事：

- 记录一条邀请：谁邀请了谁、加入哪个团队、给什么角色、什么时候过期。
- 发送邮件：把邀请链接发给对方，并处理邮件发送失败的情况。
- 校验邀请链接：判断链接是否真实、是否过期、是否已经被接受或撤销。
- 加入团队：被邀请人接受后，把他变成团队成员，并赋予正确角色。

这里最关键的是：权限、邀请状态、重复邀请、链接安全。前端可以展示按钮，但真正能不能邀请、能不能接受，必须由后端判断。

## 你需要先决定什么

- 邀请链接有效期是固定 7 天，还是团队管理员可以配置？
- 被邀请邮箱还没有账号时，是先注册再加入，还是接受邀请时自动创建账号？
- 一个邮箱被重复邀请时，是覆盖旧邀请、重新发送旧邀请，还是报错提示“已有待接受邀请”？
- 管理员撤销邀请后，对方点旧链接看到什么提示？
- 邀请时能选择哪些角色？普通成员能不能被邀请成项目管理员？
- 接受邀请后是否需要记录审计日志，比如谁邀请、谁接受、什么时候接受？

这些是业务规则，不是纯技术细节。先定下来，后端接口才不会一边做一边改。

## 它大概会有哪些接口

你可以理解成后端会提供几类“入口”：

| 你要做的事 | 给开发看的接口方向 |
| --- | --- |
| 创建邀请并发邮件 | `POST /teams/{team_id}/invitations` |
| 查看待接受邀请 | `GET /teams/{team_id}/invitations?status=pending` |
| 重新发送邀请 | `POST /teams/{team_id}/invitations/{invitation_id}/resend` |
| 撤销邀请 | `POST /teams/{team_id}/invitations/{invitation_id}/revoke` |
| 接受邀请 | `POST /invitations/{token}/accept` |

这里的 `token` 可以理解成邀请链接里的临时通行证。它不能太容易被猜到，也不要直接把敏感信息放在链接里。

## 哪些地方容易出问题

- **权限问题**：不能只靠前端隐藏“邀请成员”按钮，后端必须确认当前用户是团队管理员。
- **角色越权**：管理员能邀请哪些角色要说清楚，避免普通管理员把别人邀请成更高权限角色。
- **重复邀请**：同一个邮箱已经是成员、已有待接受邀请、旧邀请已过期，这三种情况要分别处理。
- **链接安全**：邀请 token 不要明文存库，不要写进日志，不要永久有效。
- **邮件失败**：邀请记录创建成功但邮件发送失败时，要能重试或显示“待重发”。
- **账号绑定**：接受邀请的人登录账号邮箱，是否必须和邀请邮箱一致，要明确。
- **过期和撤销**：过期、已撤销、已接受的邀请不能再被接受。

## 你可以这样问开发

- 邀请 token 会不会加密或只存 hash？
- 接受邀请时，是否强制校验登录用户邮箱等于被邀请邮箱？
- 已经在团队里的邮箱，再邀请时返回什么错误？
- 重新发送邀请是刷新有效期，还是只重发原链接？
- 邮件发送失败时，接口返回成功还是失败？后台有没有重试机制？
- 邀请记录和成员加入是否会写审计日志？

## 暂时不要做什么

- 不要先做批量邀请、通讯录导入、外部域名白名单，第一版先把单人邀请跑通。
- 不要把角色、团队 ID、邮箱完全交给前端自己判断。
- 不要让邀请链接永久有效。
- 不要把邀请 token 明文存数据库或输出到日志里。
- 不要在没定清楚“未注册用户怎么加入”前直接开工。

# 后端 Skill 经典评测 Case

这份题库用于横向评测后端开发类 Skill。Case 从易到难排列，覆盖 API 契约、已有项目改动、数据库迁移、鉴权边界、集成测试和事故排查。

评测时不要一次全跑。建议每个候选 Skill 先跑 Case 1 和 Case 2；如果表现还可以，再继续跑后面的高风险 case。

## 评分维度

每个 case 都按 1 到 5 分记录：

| 维度 | 看什么 |
| --- | --- |
| 需求澄清 | 是否主动确认角色、权限、状态流转、数据边界和非目标 |
| 设计质量 | API、数据模型、错误码、幂等、兼容性是否清楚 |
| 代码落地 | 是否贴合现有项目结构，改动是否克制 |
| 测试验证 | 是否补测试、smoke test、迁移验证或回归检查 |
| 风险意识 | 是否说明鉴权、数据库、数据隐私、回滚和上线风险 |
| 普通用户友好度 | 是否能解释清楚使用门槛、下一步和不该做什么 |

## Case 1：API 契约设计（入门）

适合测试：API 设计 Skill、后端架构 Skill、API review Skill。

任务：

```text
请设计一个“项目任务管理”后端 API。

业务背景：
- 一个团队可以有多个项目。
- 一个项目里有多个任务。
- 任务有负责人、截止日期、优先级和状态。
- 状态包括：todo、doing、blocked、done、archived。
- 成员可以评论任务。
- 普通成员只能修改自己负责的任务；项目管理员可以修改项目内所有任务。

请输出：
1. 核心资源和接口列表。
2. 关键请求 / 响应示例。
3. 错误码和状态码设计。
4. 权限边界。
5. 分页、筛选和排序方案。
6. OpenAPI 草稿片段。

不要直接写代码，先把 API 契约设计清楚。
```

重点观察：

- 是否追问项目成员角色、任务状态流转和归档规则。
- 是否避免只有 CRUD 大纲。
- 是否考虑分页、筛选、错误响应、权限和状态流转。
- 是否输出可复核的 API 契约。

## Case 2：已有项目新增接口（基础落地）

适合测试：后端开发 Skill、端到端 coding workflow。

任务：

```text
你正在一个已有 FastAPI 项目里新增“任务归档”功能。

现有约定：
- 已有 Task 模型，字段包括 id、title、status、assignee_id、project_id、created_at、updated_at。
- status 目前只有 todo、doing、blocked、done。
- 已有接口：GET /tasks、POST /tasks、PATCH /tasks/{task_id}。
- 已有鉴权依赖 get_current_user。
- 只有任务负责人或项目管理员可以修改任务。

请给出实现方案，要求包括：
1. 需要修改哪些文件。
2. 数据库字段或 enum migration 怎么处理。
3. 新增或修改哪些接口。
4. 权限判断怎么复用现有逻辑。
5. 单元测试和 smoke test 怎么写。
6. 有哪些回滚和兼容性风险。

如果信息不够，先列出需要读取的文件，不要假设项目结构。
```

重点观察：

- 是否先要求读取现有模型、路由、权限和测试结构。
- 是否不另起一套项目结构。
- 是否考虑 enum / migration / 回滚。
- 是否补测试和 smoke test。

## Case 3：REST API 质量评审（中等）

适合测试：API review Skill、后端架构 Skill。

任务：

```text
请评审下面这组 REST API 设计，找出命名、状态码、权限、分页、错误响应、幂等和版本兼容问题。

接口草稿：
- POST /project/create
- GET /project/list?page=1
- POST /project/delete?id=123
- POST /task/update
- GET /tasks/all
- POST /comment/add
- GET /user/tasks?userId=12

当前错误响应：
{
  "success": false,
  "message": "failed"
}

权限说明：
- 登录用户可以访问所有接口。
- 前端会隐藏没有权限的按钮。

请输出：
1. 严重问题。
2. 中等问题。
3. 可以后续优化的问题。
4. 建议改成什么接口。
5. 最小改造顺序。
```

重点观察：

- 是否指出前端隐藏按钮不等于后端权限。
- 是否指出 delete / update 用 POST 的兼容与语义问题。
- 是否给出可迁移方案，而不是要求一次性推翻重写。
- 是否区分严重程度。

## Case 4：数据库迁移与数据修复（进阶）

适合测试：数据库 Skill、后端开发 Skill、工程 workflow。

任务：

```text
现在任务表 tasks 有 120 万行，需要新增 archived_at 和 archived_by 两个字段，并把历史 status='archived' 的任务补齐 archived_at。

限制：
- 数据库是 PostgreSQL。
- 线上写入不能停。
- 已有 status 字段上有索引。
- 需要支持回滚。
- archived_by 可以为空。
- 历史数据只能用 updated_at 近似 archived_at。

请给出 migration 方案和上线步骤。
要求说明：
1. DDL 是否会锁表。
2. 是否需要分批 backfill。
3. 索引是否需要调整。
4. 应用代码兼容顺序。
5. 验证 SQL。
6. 回滚方案。
```

重点观察：

- 是否知道大表 DDL 和 backfill 风险。
- 是否分阶段上线：先加字段、再双写/兼容、再回填、再切逻辑。
- 是否提供验证 SQL 和回滚思路。
- 是否避免让用户直接在生产库一次性 UPDATE 全表。

## Case 5：鉴权边界与越权风险（进阶）

适合测试：后端安全 Skill、API 设计 Skill、后端开发 Skill。

任务：

```text
有一个接口 PATCH /tasks/{task_id} 用于修改任务标题、状态和负责人。

现有规则：
- 普通成员只能修改自己负责的任务标题和状态。
- 项目管理员可以修改项目内所有任务。
- 只有项目管理员可以改负责人。
- archived 任务不能再修改。

请设计后端权限判断逻辑，并说明测试用例。
要求输出：
1. 权限判断顺序。
2. 需要从数据库读取哪些信息。
3. 哪些字段允许普通成员修改。
4. 错误码和错误信息。
5. 至少 8 个测试用例。
```

重点观察：

- 是否区分“能访问任务”和“能修改某字段”。
- 是否考虑 archived 任务优先拒绝。
- 是否避免只依赖前端传来的 role。
- 是否能给出字段级权限测试。

## Case 6：生产事故排查（高难）

适合测试：后端排障 Skill、日志分析 Skill、工程 workflow。

任务：

```text
线上从 10:05 开始，PATCH /tasks/{task_id} 的 500 错误率从 0.1% 升到 8%。

已知信息：
- 10:00 发布了任务归档功能。
- 10:03 数据库 CPU 从 35% 升到 85%。
- 10:04 p95 latency 从 180ms 升到 2.4s。
- 错误日志里有：invalid input value for enum task_status: "archived"。
- 有少量请求超时。

请给出排查和止血方案。
要求输出：
1. 可能原因排序。
2. 立即止血动作。
3. 需要查哪些日志 / 指标 / SQL。
4. 如何判断是否需要回滚。
5. 事后修复和补测试建议。
```

重点观察：

- 是否能把 enum migration、应用发布顺序和数据库压力联系起来。
- 是否先止血，而不是直接继续开发。
- 是否要求查发布版本、迁移状态、慢 SQL、错误分布。
- 是否能给出回滚判断。
